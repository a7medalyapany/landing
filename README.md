# Landing Boilerplate — Next.js 16 + Payload CMS 3 + Postgres

A starter for CMS-driven landing sites, set up for **AI-assisted development with
Claude Code**. You get two things:

1. **The app:** Next.js 16 (App Router) with Payload CMS 3 embedded (admin at `/admin`),
   Postgres, and Vitest + Playwright tests.
2. **The AI workflow layer:** project rules, guardrail hooks, review agents, skills and
   MCP servers. With these, Claude Code plans, verifies with evidence and asks before
   doing anything risky. See [`docs/ai-workflow.md`](docs/ai-workflow.md).

> This is a starting point. The content model is still the Payload blank template
> (`Users`, `Media`). The plan for building it out is in
> [`docs/execution-roadmap.md`](docs/execution-roadmap.md).

---

## Requirements

- **Node** `^22.23.4` or `>=24.22.1`, and **pnpm** 9–11 (`corepack enable`)
- **Postgres** 15+. The easiest way is Docker or Podman via the included `docker-compose.yml`;
  a hosted one (Neon, Supabase, RDS…) works too.
- **Claude Code** (optional but recommended), plus `jq` for the hooks
  (`sudo dnf install jq` / `brew install jq` / `apt install jq`)

## Quick start

This is a GitHub **template repository**: each new project starts as its own repo with
a clean history. Don't clone this repo to build on it directly.

**Create your project**, either way:

- On GitHub, click **Use this template** → **Create a new repository**, then clone your new repo.
- Or with the GitHub CLI (creates, then clones into `./my-site`):

  ```bash
  gh repo create my-site --private --template a7medalyapany/landing --clone
  ```

Then, inside your new project:

```bash
cd my-site
pnpm install
cp .env.example .env          # then edit the values
```

Edit `.env`:

```env
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5432/landing
PAYLOAD_SECRET=<long random string>   # e.g. `openssl rand -hex 32`
```

Start Postgres, then the app:

```bash
docker compose up -d postgres   # Postgres 17 on localhost:5432 (podman compose works too)
pnpm dev
```

Open `http://localhost:3000` for the site and `http://localhost:3000/admin` for the admin.
The admin asks you to create the first user. In dev, Payload creates the tables
automatically.

**Other ways to run it**

- **Everything in containers:** `docker compose up` runs Postgres and the app (in a Node
  container), so you don't need Node installed. The compose file points the app at the
  `postgres` service for you.
- **Hosted Postgres** (Neon, Supabase…): skip compose and put that connection string in
  `DATABASE_URL`.
- **Port 5432 already taken?** Change the left side of `'5432:5432'` in
  `docker-compose.yml` (e.g. `'5433:5432'`) and use the same port in `DATABASE_URL`.
- **Reset the local database:** `docker compose down -v` deletes the data volume.

## Tests

Tests **never** use your dev database. They run against `TEST_DATABASE_URL` and refuse to
start if it's missing or the same as `DATABASE_URL`. That way a test run can't wipe dev
data, or create its test admin user in production.

- `docker compose` creates the `landing_test` database automatically the **first** time the
  volume is created. If your volume already existed, create it once with:
  `docker compose exec postgres createdb -U postgres landing_test`
- With hosted Postgres, create a second database (or a Neon branch) and use that.
- e2e needs a browser, installed once: `pnpm exec playwright install chromium`.
- `pnpm test:e2e` starts its own dev server on **:3001**, pointed at the test database.
  Next.js allows only one dev server per folder, so **stop `pnpm dev` first**.

## Scripts

| Command | What it does |
|---|---|
| `pnpm dev` | Dev server (Payload pushes the schema to the local DB automatically) |
| `pnpm build` / `pnpm start` | Production build / serve |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm lint` | ESLint |
| `pnpm test` | Integration (Vitest) + e2e (Playwright) |
| `pnpm test:int` / `pnpm test:e2e` | Run each suite separately |
| `pnpm generate:types` | Regenerate `src/payload-types.ts` after schema changes |
| `pnpm generate:importmap` | Regenerate the admin import map after adding admin components |
| `pnpm payload migrate:create <name>` | Create a migration from schema changes |
| `pnpm payload migrate` | Apply migrations (production: follow the runbook) |

## Project structure

```
src/
  app/(frontend)/      # the public site (your pages go here)
  app/(payload)/       # Payload admin + API — GENERATED, don't edit (except custom.scss)
  collections/         # Payload collections (Users, Media)
  payload.config.ts    # Payload config (Postgres adapter, Lexical editor)
  payload-types.ts     # GENERATED by `pnpm generate:types`
tests/                 # int (Vitest) and e2e (Playwright)
docs/                  # the spec: architecture, roadmap, decisions, runbooks
.claude/               # Claude Code workflow layer (see below)
.mcp.json              # MCP servers for Claude Code
CLAUDE.md              # project rules every Claude session reads first
```

## Working with Claude Code

Open the repo in Claude Code and it picks everything up automatically. The full
explanation is in [`docs/ai-workflow.md`](docs/ai-workflow.md). Summary:

| Piece | Where | What it does |
|---|---|---|
| Project rules | `CLAUDE.md` | Stack, commands, code boundaries and must-follow rules. Keep it short. |
| Permissions | `.claude/settings.json` | Tests, lint and typecheck run without prompts; `git push`, migrations and deploys ask first; `.env` and `rm -rf` are blocked |
| Hooks | `.claude/hooks/` | Block edits to generated files and `.env`; after every TS edit, run typecheck and flag `'use client'` on pages/layouts |
| Agents | `.claude/agents/` | `researcher` (read-only explorer) and `governance-reviewer` (reviews work it didn't write: PASS/FLAG/BLOCK) |
| Command | `/build-page <name> [design-ref]` | Builds one page end to end, with approval stops after the plan and after the review |
| Skills | `.claude/skills/` | `payload` (CMS reference), `nextjs-frontend` (Server Components first, `'use client'` only when needed), `verify-frontend-change` (real-browser checks), `rtl-bilingual-component` (RTL and localization rules) |
| MCP | `.mcp.json` | `context7` (current docs), `playwright` (browser), `github` |

**One-time setup for MCP:** the `github` server needs a token in your shell (not in `.env`):

```bash
export GITHUB_PERSONAL_ACCESS_TOKEN=ghp_...   # add to ~/.zshrc or ~/.bashrc
```

Claude Code asks you to approve the project's MCP servers the first time. Run `/mcp`
to check them.

**Personal settings** go in `.claude/settings.local.json` (git-ignored), not in the
shared `settings.json`.

### The workflow loop

1. **Plan:** pick a task from `docs/execution-roadmap.md`.
2. **Build:** use `/build-page` for pages, or just prompt for small things.
3. **Verify:** run the tests and check the page in a real browser.
4. **Review:** the `governance-reviewer` agent checks the work.
5. **Ship:** commit the code, migration and doc updates together, and tick the roadmap.

For one-line fixes, skip the ceremony and just ask.

## Making it your own

1. Rename the project in `package.json` (`name`, `description`) and the database name in
   `docker-compose.yml`, `docker/postgres/init/01-test-database.sql` and `.env` if you
   like (`landing` → your project).
2. Fill in [`docs/architecture.md`](docs/architecture.md) (overview, data model, access
   rules) and adjust the roadmap. The agents read these, so the better they are, the
   better Claude's output.
3. Add your project's own must-follow rules to `CLAUDE.md` (keep it short).
4. Record big decisions in `docs/decisions/` (copy `0000-template.md`).
5. When a bug bites twice, write it down in `docs/debugging-notes.md`, and consider
   turning it into a skill or hook.

## Database & migrations

- **Local dev:** Payload's push mode syncs the schema automatically. No migrations needed.
- **Any schema change you'll ship:** run `pnpm generate:types` and then
  `pnpm payload migrate:create <name>`, and commit both with the change.
- **Production:** apply migrations by hand only, following
  [`docs/runbooks/prod-migrations.md`](docs/runbooks/prod-migrations.md).
- Why Postgres: [`docs/decisions/2026-10-29-postgres-over-mongodb.md`](docs/decisions/2026-10-29-postgres-over-mongodb.md).
